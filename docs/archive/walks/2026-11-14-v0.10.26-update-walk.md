# In-app update walk — 0.10.25 → published 0.10.26, 2026-11-14

The update path walked on the release after `docs/archive/walks/2026-10-31-v0.10.25-update-walk.md`. On the Windows VM
it went the same way: smoke group AC's rows *Offered on launch*, *The install* and *Up to date* (all already ticked),
the proxy rows skipped. This time the Linux VM walked it too, as an AppImage, with the watcher of the v0.10.21 release
gate (`docs/archive/walks/2026-10-07-v0.10.21-release-gate-linux.md`) and the checks of smoke group BI row 8. Both VMs
were driven over Remote Control and reported back; nothing was ticked or committed there. Every reading below was
measured on the VM unless it says otherwise.

Against BI row 8 as written, the Linux walk ran under Xvfb with `dbus-run-session`, as the v0.10.21 gate did, not on
the desktop's display; it made no separate Quit of 0.10.25 before the update; and it read the mount count about a
minute after the restart, not a few seconds.

It is the second of the two walks `docs/plans/open-items.md` §AM waited for. 0.10.25 is the first release that carries
`tauri-plugin-updater` 2.14.0 and `minisign-verify` 0.3.0 (its `Cargo.lock`), and the installed copy is the one that
verifies and installs an update, so this is the first update those two run. 0.10.26 carries the updater's 2.14.1
(#42), which first runs on the update after this one (`docs/plans/open-items.md` §AW).

    source, not run). The payload arrives in memory. For each temp location in turn (the system's, the cache
    folder, the image's own folder) the updater makes a `tauri_current_app` directory and uses it only if it is on

    image's path with `std::fs::write`, which creates a new file there; if the write fails it renames the old image
    back. The directory is removed when the install returns. So the new inode, the directory beside the image and
    the missing download file are all what the code does, and between the rename and the new file the path does
    not exist for a moment, shorter than the 10 ms sampling could see.

    v0.10.21 gate's "dropped to 0 bytes, rewritten in place" was, by the source, the new file caught just after it
    was made; that gate's watcher read size and mtime, not the inode. What differs between the walks is the time the
    write took: about 0.43 s at the v0.10.20 gate, about 1 s at the v0.10.21 gate, about 0.1 s here, on three

### Not reached

A working update reaches none of these changes of 2.14.0; all stay read from its changelog and source only:

- the refusal of a payload that is not an AppImage (by the source, the accepting side of that check ran: the payload
  is one);
- the fallback to the next temp location when a location's directory cannot be created. Moving past a location on
  another device is older than 2.14.0. This walk moved past two locations: the system's temp folder, on tmpfs, and
  the cache folder, whose filesystem is known from its path only, so a missing cache folder, which is the new
  fallback's case, is not ruled out;
- the retry after a rename that fails across mounts (`os error 18`). The updater already skips a temp location on
  another device, in 2.13.1 too, so ext4 against tmpfs is not that case: it needs one device under two mounts, such
  as a bind mount. This walk's setup could not reach it;
- on Windows, the message when the installer fails to start;
- `check()` answering "no update" for a release with no entry for this platform.
