# AppImage release gate, v0.10.15 on Linux — 2026-10-01

The AppImage release gate for **v0.10.15**, walked like the v0.10.14 one
(`docs/archive/walks/2026-09-29-v0.10.14-release-gate-linux.md`): the installed 0.10.14 AppImage updates itself to
0.10.15 through the app. This is the first update that can restart by itself, because the restart is run by 0.10.14,
which carries the env-scrub fix. Host: Ubuntu 26.04.1, kernel 7.0.0-34, GNOME on Wayland, VMware SVGA II,
uutils coreutils 0.10.0. The same VM as the 0.10.13 and 0.10.14 gates and group BI.

## Findings

1. **The 0.10.14 → 0.10.15 update installs in place and restarts by itself.** This is the first Linux AppImage
   update to do both.
   - The new `AppRun` started normally, with no `/usr/bin/env` / `libsystemd` error. Reading, not verified (the
     spawn's own environment wasn't captured): 0.10.14 scrubbed the old image's variables before spawning.
   - The old image unmounted at 18:44:34.205, before the watcher's first sample showing the new pid (.273).
   - The restart inherits the launching environment, which is why `WEBKIT_DISABLE_DMABUF_RENDERER=1` carried over.
     Not tried: a restart from an app launched without that variable. On this VMware desktop it would open blank
     (finding 3 of the 0.10.14 gate).
2. **Nothing new from apport or the kernel.**
   - The journal does show AppArmor `DENIED` lines for `fusermount3` (`dac_override`, `setuid`) at each unmount.
     These come at every AppImage unmount on this VM, back to 2026-09-29, so they don't come from this release.
3. **A watcher artifact, not a finding.** The watcher printed one stamp out of order (`18:44:34.561` between .986 and
   .127). The cause: uutils `date` 0.10.0 drops the leading zero of `%3N`, so `date -d @1.056 +%S.%3N` prints
   `01.560`. That stamp is really 18:44:34.056. The stamps above use the journal's own times where they can.
