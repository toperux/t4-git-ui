- **`tauri-plugin-single-instance` 2.5.4 → 2.5.5, the one that needs a fix (D1):**
  - **#3482: the lock is let go later, on every exit and every OS.** 2.5.4 released the lock (the D-Bus name on
    Linux, the mutex on Windows, the socket on macOS) in its own handler for `RunEvent::Exit`, which Tauri runs
    *before* the app's exit handler. 2.5.5 keeps the lock in the app's resource table and releases it in
    `cleanup_before_exit`, which Tauri runs *after* the app's exit handler returns (read: the plugin's
    `lib.rs:56-80`, `platform_impl/linux.rs:15-29`; `tauri` 2.12.5 `app.rs:1128-1140`, `:1449-1455`, `:2811-2815`).
  - **What that breaks: the AppImage update's relaunch.** After an in-app update of the Linux AppImage, the app's
    exit handler starts the new image (`src-tauri/src/lib.rs:324-343`, the spawn at `:334-337`), and its comment at
    `:326-328` relies on the name being free by then. With 2.5.5 the new image starts while the old process still
    holds the name. If the new one reaches the plugin's setup first, it finds the name taken and calls the dying
    process (`platform_impl/linux.rs:94-117`). What happens then is the next bullet's hand-over: the new copy
    exits, hangs, or panics if the old one leaves the bus mid-call (`lib.rs:313`). In every case **the app does
    not come back after the update.** The window is the time the old process needs to finish its handler and
    clean up, against the new image's mount and start: probably a few milliseconds against hundreds, so probably
    rare (reasoned; not measured: D5 forces the race to show that the fix closes it).
  - **What it changes for an ordinary quit (D4, D8).** A start that lands while the old copy is still in its exit
    handler (`lib.rs:324-344`: the layout write, the log shutdown) or in the cleanup now finds the lock held and
    hands over to the dying copy. Under 2.5.4 that same start became a second app that could read `layout.json`
    while the first was still writing it, which is the case #3482 is there to remove. A few milliseconds
    (reasoned); on every OS (read for Linux and Windows; macOS's socket read, not walked).
    - **On Linux the hand-over can hang both copies (read in review pass 4, not run).** Our callback
      (`lib.rs:153-163`) asks a window whether it is minimized (`commands/window.rs:456-463`), which waits for
      the main thread; that thread has left the event loop and is in the exit handler. It then runs the cleanup,
      whose release of the name waits for a reply that only the bus connection's one worker thread can deliver,
      and that thread is the one stuck in our callback (zbus's single executor thread; no call timeout by
      default). The old app stays frozen on the name and the new start waits with no window. 2.5.4 had the same
      trap for a call still inside the callback when the exit began: the callback makes about eight round trips
      to the main thread and writes `layout.json` (`commands/window.rs:205`, `:215-222`, `:343`, `:353-356`,
      `:456-469`), so that window is about a millisecond (reasoned).
    - **With D8's guard** the callback no longer waits on the main thread at all: it hands its work to the main
      thread (`run_on_main_thread`) and returns at once, and the work itself does nothing when the app is exiting
      (`AppState::exiting`, `state.rs:50`, raised at `lib.rs:317-320` on every exit through the event loop: Quit,
      the last window closed, the update's exit or restart; read. The Windows update ends the process without
      one, and there the callback cannot hang). So the
      call is always answered, the new copy exits and the old one finishes: nothing opens, which is what D4
      accepts, and no timing can catch the callback mid-run. `spawn` is written to be called on the main thread
      (`window.rs:171-175`: it builds the window on a worker thread). On Windows the hand-over already arrives on
      the main thread through a message window, and a second copy that gets no answer exits (read).
  - **The Windows update path, also changed but harmless.** The updater runs the app's `cleanup_before_exit`
    through its `on_before_exit` hook just before it starts the installer (updater `lib.rs:119-122`,
    `updater.rs:1017-1019`, then `ShellExecuteW`, then `process::exit` at `:1050`). Under 2.5.4 that left the mutex
    held until the process ended; under 2.5.5 it drops the lock there, a moment earlier. The installer's relaunch
    is unaffected (reasoned). One new corner (D7): if starting the installer fails, the app, whose windows the
    cleanup has already hidden (as before), now also runs on without its lock. A start after that used to open a
    start-screen window in the hidden copy; now it becomes a second full app that restores the saved layout while
    the first lingers hidden (reasoned; not run, and it needs Windows to refuse a just-verified setup exe). macOS:
    `app.restart()` (`commands/update.rs:226`) restarts after the cleanup (`app.rs:1449-1455`; read, cannot be
    walked).
  - **#3704, Windows.** A second copy now waits up to 1 s (40 × 25 ms) for the first copy's hidden message window
    and then always exits; before, a second copy that missed the window carried on as a second, independent app.
    The gap it closes is microseconds wide, inside the first copy's plugin setup, so it is read, not walked. Our
    callback (`lib.rs:153-163`) ignores the arguments and opens a new start-screen window. Step 6's row e walks
    the ordinary hand-over.
- **`tauri-plugin-dialog` 2.8.3 → 2.8.4, with `rfd` 0.16.0 → 0.17.2.** The plugin's only change is the `rfd` bump.
  Every native dialog in the app goes through it: the folder pickers (`StartScreen.tsx:89`, `:94`,

  - **Windows: every dialog is on rewritten code.** `rfd` 0.17 dropped its hand-written futures; a picker or a
    message box now runs the synchronous dialog on a new thread and answers through a one-shot channel
    (`win_cid/file_dialog.rs`, `win_cid/message_dialog.rs:236-248`; a dropped sender reads as Cancel). The dialogs

  - **macOS: the same rewritten plumbing under every picker and box.** Cannot be walked. See D3.
- **`tauri-plugin-updater` 2.14.0 → 2.14.1, with `zip` 4.6.1 → 9.3.0 and `base64` 0.22.1 → 0.23.1.** The plugin's
  `src/` is identical between the two; only its two dependency lines moved (read).
  - **`zip` is compiled into the Windows build only** (a `cfg(windows)` optional dependency behind the default `zip`
    feature) and is called from one place, when the downloaded update starts with the zip magic bytes
    (`updater.rs:1121-1160`). Ours is the bare NSIS setup exe (`tauri.conf.json:30` `createUpdaterArtifacts: true`;
