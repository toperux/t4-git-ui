## What 8.2.2 changes

Read from the three crates as published on crates.io (8.2.0, 8.2.1, 8.2.2, unpacked side by side) and from upstream's
release notes. Nothing below was run.

- **Linux: nothing.** `inotify.rs` in 8.2.2 is 8.2.1's but for one format string (a one-line diff, `:137`). Every queued
  removal still makes a pass over all watched paths (`:379-383` calling `:486-498`), and the INFO line is still there
  (`:529`). October's reading stands, and the row's trigger "a release that skips the removal scan" has not fired.
- **Windows: a fix for a race the held 8.2.0 has.** The release notes: "prevent watch shutdown from rearming reads on
  closed handles, which could deadlock when handles are reused" (upstream #1052, for #1051).
  - 8.2.0 and 8.2.1 stop a watch the same way (`windows.rs:255-268`): cancel the read, close the directory handle, then
    wait for the read's completion. A completion that was already queued as successful runs during that wait and starts
    the next read on the closed handle (`:331-371`).
  - Normally that read fails at once and the wait ends (`:319-326`). If another thread has been given the same handle
    value in between, the read starts on a foreign handle and the wait may never end.
  - **The window is narrow.** The server thread runs completions whenever it waits (`:154`, every 100 ms at most), so a
    successful completion is still queued at the stop only if the read completed in the instant between that wait
    returning and the cancel: microseconds. The handle value must also be reused inside the same instant.
  - 8.2.2 marks the watch as stopping first, so a queued completion does not start a read, and closes the handles only
    after the wait. It also fixes a second reuse of a closed handle: 8.2.0 sends the stop and then wakes the server,
    which may have closed the wake-up handle by then (`:161-164`, `:590-595`); 8.2.2 wakes first.
- **What that race means in this app (reasoned; never seen or reported; no rate known).** A watch stops when a
  repository closes (`crates/git-core/src/watch.rs:264-277`). Nothing waits for `notify`'s thread there
  (`stop_nonblocking` joins nothing), so the bad case is not a frozen window: it is one stuck thread and its handles
  until the app exits, and, only for a repository whose git directory lies outside its work tree (`watch.rs:231-236`),
  possibly a second watch that was never stopped. Given the two instants that must coincide, it is expected to be very
  rare.
- **macOS: 8.2.1's change, unchanged.** No macOS file differs between 8.2.1 and 8.2.2, so 8.2.2 still brings the
  FSEvents backend swap (`fsevent-sys` → `objc2-core-services`) that the hold has kept out. There is no Mac to walk it
  on.
- **The toolchain floor moves from Rust 1.85 to 1.88: no issue.** CI and the release build install `stable`
  (`checks.yml:63`, `release.yml:140`), no manifest sets `rust-version`, and the local toolchain is 1.99.0.
- **`notify` 9.0 is close but not out:** 9.0.0-rc.8 is from 2026-11-09. On upstream's main branch (`6cf4c8f141`,
  2026-11-10) the Linux removal path is rewritten: the "already removed" line became a trace, so the log lines are gone,
  but every queued removal still makes a pass over all watches (read: `inotify.rs:875-886`, `:1248-1255`, `:1301-1308`
  there). Its cost on a mass delete is unread, and it needs `notify-debouncer-full` 0.8, also a release candidate.

**What this changes since October.** Then, 8.2.1 offered the app nothing it uses. Now the newer version fixes a real, if
very rare, race on Windows, and holding keeps it. That Windows is where most of the app's use is, is the owner's to say,
not measured. The Linux cost is still only reasoned. So the case for measuring is a little stronger than it was, not
urgent.

## Decisions

Both ruled by the owner, 2026-11-11, after review pass 1.

- **N1. Thursday's Dependabot run: (a), 8.2.2 added to the `ignore` entry.**
  - **(a) Add 8.2.2 to the `ignore` entry before the run.** `versions: ["= 8.2.1", "= 8.2.2"]`, pushed
    before 2026-11-12 12:25 UTC. The cargo group's PR then comes without `notify`, as #42 did. It decides nothing about
    8.2.2 itself: N2 does. It keeps October's design, in which a PR is the signal that a new version is out. Cost: one
    small push; the same edit for every later 8.2.x until the hold lifts; and `notify` 9.0.0, once stable, still arrives
    in the group's PR, where it probably fails to build unless `notify-debouncer-full` 0.8 comes with it (reasoned, not
    checked).
  - Not taken: (b) ignore every later version in one edit: `versions: [">= 8.2.1"]`. No further edits, and 9.0 never
    breaks the group's PR. Cost: no PR ever says a new `notify` is out, so someone has to look by hand; the open row's
    trigger would become a dated check.
  - Not taken: (c) let Thursday's PR come with 8.2.2 in it. It is read, not merged. To merge the rest of the group, the
    hold commit goes on the PR's branch again (the lock's `notify` hunks undone), as on #38: about an hour with its
    checks.
  - **A side effect of (a):** a push that changes `dependabot.yml` starts Dependabot runs at once (the #38 merge
    did, `open-items-done.md` §AV), so the cargo and npm PRs may open on the push, not on Thursday. Whatever opens is
    read, not merged, and goes to the owner.
- **N2. What to do about 8.2.2: (a), measure first.**
  - **(a) Measure the Linux cost with a small standalone program on the Linux VM, then decide with numbers.** Step 2:
    8.2.0 against 8.2.2, a tree of up to 30 000 directories deleted under a recursive watch, the same watcher setup as
    the app's. About 45 minutes of VM time, no change to the repository. It answers the one thing that is only reasoned.
    Then the owner rules: lift the hold (its own plan, with a Windows and a Linux walk and the macOS gap) or keep it.
  - Not taken: (b) keep holding and do not measure, until `notify` 9.0 is stable. No work now. Windows keeps the stop
    race, and the 9.0 line's Linux cost is as unread as 8.2.2's.
  - Not taken: (c) lift the hold now, unmeasured. The Windows fix lands soonest. The risk is the Linux one the hold was
    made for: a stalled watcher and thousands of log lines on a mass delete, found by a user and not by us.

Three more, ruled by the owner on 2026-11-11 with the measurement's numbers (step 3):

- **N3. Lift the hold or keep it: (a), the hold at 8.2.0 stays.** After a mass delete 8.2.2 reported the next change
  after 3.7 s at 10 000 directories and 10.8 s at 30 000, against 1.3 s for 8.2.0, its thread's CPU time almost equal to
  the wait, with about 2 800 Info lines per delete. The Windows stop race stays with the hold. The reopen trigger, as
  the option put it: a `notify` release without the per-removal pass, or the Windows race seen. Not taken: (b) lifting
  to 8.2.2 through its own plan.
- **N4. The second set of runs, with the kernel queue raised: (a), skipped.** Every run overflowed the default queue,
  so step 2 asked for it. It needs `sudo` on the VM, and it could only show a higher cost for 8.2.2, so it could not
  change N3. Not taken: (b) the owner running the `sysctl` on the VM for 12 more runs.
- **N5. Reporting the removal pass upstream: (a), a draft for the owner to read.** No issue on `notify-rs/notify`
  covers it (searched 2026-11-11). Posting is asked separately. Not taken: (b) no report.

## Steps

1. **The `ignore` entry (N1 (a)).** In `.github/dependabot.yml`, the cargo entry's `versions: ["= 8.2.1"]` becomes
   `versions: ["= 8.2.1", "= 8.2.2"]`, and the comment above it says "8.2.1 and 8.2.2 scan" and names this plan beside
   October's. Nothing else changes: the manifest pin and the lock already say 8.2.0.
   - Verify before the push: the file parses and the entry holds the two versions (`python -c` with `yaml`, which is
     installed; the repository has no YAML parser for node); a change review of the one-line diff (CLAUDE.md step 5).
   - Commit: `build(deps): hold notify at 8.2.0 over 8.2.2 too`, body: `8.2.2 keeps 8.2.1's Linux removal scan.` Push on
     the owner's go, before the run.
   - Verify after the push: GitHub's Dependabot page shows no config error; the cargo PR, when one opens (on the push or
     on Thursday), touches neither `notify` in `Cargo.lock` nor the pin in `crates/git-core/Cargo.toml`.
2. **The measurement (N2 (a)),** on the Linux VM (session `git-ui-lin`), in its scratchpad, never in the repository.
   - **The program.** One small cargo project built twice in release mode, with `notify = "=8.2.0"` and `"=8.2.2"`, both
     with `notify-debouncer-full = "0.7"`. It sets the watcher up as the app does (`watch.rs:220-230`:
     `new_debouncer_opt` with `NoCache`, the app's debounce time, `RecursiveMode::Recursive` on the root). It installs a
     `log` logger capped at Info, the app's own filter (`src-tauri/src/lib.rs:26`), that counts records by level and
     first words. For every delivered batch it records the arrival time and whether the batch carries the rescan flag.
   - **The tree.** N directories shaped like an installed `node_modules` (three levels, two files each), for N = 10 000
     and 30 000, built before the watch starts; `watch()` returns once it has walked the tree, so the tree is watched
     from then.
   - **Before the runs, recorded:** `fs.inotify.max_user_watches` (must be above N; if not, the largest N that fits is
     used) and `fs.inotify.max_queued_events` (16 384 by default).
   - **A run,** each in its own process, so a thread still busy does not leak into the next. Start the watch on a root
     that holds only the tree's top directory; `rm -rf` that top directory from a shell; from the moment `rm` returns,
     write a new probe file directly in the root once a second, until a batch naming one arrives or 120 s pass. Then
     read the counters.
     - The probe goes in the root itself because the root's watch stays live: a removal pass drops only paths under the
       deleted directory (`inotify.rs:488-489`). A file in a fresh subdirectory would be missed, since the subdirectory
       gets its own watch only after the backlog and the passes, and files already in it are not reported.
     - It repeats because an overflowed kernel queue drops whatever is written while it is full (`:212-215`).
     - A quiet period is not used as the end: the removal passes run after a read's events are handed on
       (`:358-383`), so a thread busy in them looks quiet.
   - **Measured per run:**
     - the delete's own wall time;
     - **the probe's latency,** from `rm`'s return to the first probe that arrives: how far the watcher is behind when
       the delete ends, and the proof that it still works; ">120 s" if none arrives, with the CPU reading kept. Every
       value carries the debouncer's own delay, about 0.25 to 0.31 s even on an idle watcher, the same for both
       versions, so the numbers compare as they are; the one-second spacing matters only when a probe is lost to an
       overflow;
     - the CPU time of the watcher's thread up to the probe's arrival, in nanoseconds
       (`/proc/<pid>/task/<tid>/schedstat`; the thread's name reads `notify-rs inoti`, cut to 15 bytes);
     - log records by level. For 8.2.2, the count of "unable to remove watch descriptor" lines against N, one per
       removal pass, shows how many passes ran. 8.2.0 logs nothing there (it drops that error, `inotify.rs:380`), so
       for 8.2.0 an overflow shows only as the rescan flag;
     - whether any batch carried the rescan flag, that is whether the kernel's queue overflowed.
   - **Runs:** three per version and size on a fresh tree, at the VM's default queue size, which is what a user has. An
     overflow is itself a result (the app then refreshes everything), but it hides the pass's cost, because lost delete
     events mean fewer passes and the slower version loses more. So if runs overflow, the same set runs once more with
     `max_queued_events` raised (it needs root on the VM; if that is not available, the record says so and the
     overflowed runs are marked not comparable on CPU time).
   - **The report:** a table of medians per version, size and queue setting, and the raw rows. It says what was measured
     and what was not: one VM, one filesystem, no app around the watcher, and a root that holds only the tree, so fewer
     watched paths than a real repository with its `.git` and sources beside it.
   - Nothing in the repository changes in this step, so it has no change review; the report goes to the owner as it is.
3. **The ruling.** The numbers go to the owner with a recommendation; the plan sets no threshold in advance:
   - if 8.2.2's probe latency and CPU time at 30 000 directories are close to 8.2.0's, the recommendation is to lift the
     hold, through its own plan: the manifest pin, the `ignore` entry and the lock together, the gates, a Windows walk
     (the watcher under load, and tabs closed during file changes for the stop path), a Linux walk (a mass delete inside
     the app, the log's line count) and the macOS backend swap as an accepted gap or a reason to hold;
   - if not, the hold stays, the row gets the numbers, and reporting the pass upstream is raised with the owner.
4. **Records,** pushed on the owner's go: `open-items.md` §AV's row updated (8.2.2 read; the Windows race the hold
   keeps; the ignore entry as ruled; the measurement and the ruling; the reopen trigger as ruled); the measurement's
   report as `docs/archive/walks/2026-11-1x-notify-8.2.2-measurement.md`; this plan archived.
