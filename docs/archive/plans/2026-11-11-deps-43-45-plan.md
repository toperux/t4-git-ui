### #45: `jsdom` 30.1.3 → 31.0.0 (a major; the tests' environment only)

- `jsdom` is a dev dependency used by `vitest` (`vitest.config.ts`: `environment: "jsdom"`, no setup files). It is not
  in the app's bundle, so nothing a user runs changes.
- **The lock (read):** `jsdom` 31.0.0; `entities` 8.0.0 → 9.0.0, `parse5` 8.1.0, `undici` 8.12.4, `whatwg-url` 17.3.0;
  13 packages removed (the old CSS stack: `css-tree`, `@asamuzakjp/*`, `@csstools/*` and others) and 6 small ones
  added. `engines` is unchanged and fits Node 24.
- **Upstream's three breaking changes against this suite (read):**
  - **The canvas backend moves to `@napi-rs/canvas`.** No effect: the app installs neither canvas package, and the one
    test that reaches a canvas mocks `getContext` (`RevisionGrid.test.tsx:96`).
  - **A new CSS engine** for parsing, selectors and computed styles; "CSS serialization and computed values can
    differ". The app's stylesheets never reach `jsdom` (`vitest` turns them into empty modules), so this touches only:
    one `getComputedStyle` read of a custom property (`useThemeTokens.test.ts:15-32`); three assertions on inline
    styles (`FileContent.test.tsx:150`, `Menu.test.tsx:273`, `DiffViewer.test.tsx:175`); selector matching in tests and
    in `Dialog.tsx` and `Menu.tsx` (`:scope >`, `[class*=…]`, `:disabled`, `[hidden]`); and the default styles that
    hide a `hidden` element from `getByRole`. All of these passed in #45's CI.
  - **The parser can pause at blocking scripts.** No effect: no test builds a `JSDOM` itself, and `vitest`'s page has
    no script.
- **Two changes to focus reach the suite (read, both versions' sources):**
  - **`jsdom` 31 moves the focus off an element that became disabled or hidden.** A new `focusFixup`
    (`lib/jsdom/living/helpers/focusing.js:212-218`) is called from a 60-per-second interval that runs while a focus
    check is pending (`Window.js:620-646`), started by any DOM change or focus change while an element has the focus.
    The check runs at the interval's next tick: about 17 ms at the soonest, and only once the test yields to the event
    loop, so never inside synchronous test code and possibly during a `waitFor`. Then the focus drops to `<body>`.
    `jsdom` 30 left the focus on the disabled element. A removed element is not part of this: both versions move the
    focus off it at once, with no blur event.
  - **`blur()` now works on an element that can no longer take the focus.** `jsdom` 30 returned early there
    (`focusing.js:194`); 31 drops that guard. So under 31 a `blur()` on a disabled button puts the focus on `<body>`
    and fires `blur` and `focusout`, at once.
- **Five comment sites, covering 12 tests, describe the old behaviour.** Four say that a focused control which disables
  itself keeps the focus in `jsdom`, so the test calls `blur()`: `SettingsDialog.test.tsx:42-53` (a helper, 4 tests),
  `StashesDialog.test.tsx:175-191` (1), `CommitPanel.test.tsx:1476-1489` (a helper, 3), `dialogs.test.tsx:793-797` (1).
  The fifth, `Dialog.test.tsx:89-113` (3 tests), says the same but blurs an enabled field, which worked in both
  versions.
  - **Under `jsdom` 30 the four sites' `blur()` did nothing:** the focus stayed on the disabled control. Those 9 tests
    passed because they send the key event straight to `document.body`, which is all `Dialog.tsx:131` looks at. So the
    comments' claim that `blur()` gets the focus to `<body>` was already untrue.
  - **Under 31 they run with the focus really on `<body>` for the first time,** and each `blur()` now fires a real
    `blur` and `focusout` into the app's handlers. They passed in #45's CI. Their names still say what they test (Esc
    from `<body>` closes the dialog); their comments are untrue in a new way. See decision D.
- **One more test is exposed:** `CommitPanel.test.tsx:217-238`, "staging a row the focus was on hands the focus back
  to the list". It focuses the Stage button, which disables during the operation, fires a blur by hand, awaits, and
  then asserts where the focus is. Under 31 a real blur can also arrive from the focus check during those awaits,
  depending on the machine's speed. The handler (`FilesColumn.tsx:418-431`) keeps its state for a disabled target, so
  it should pass either way (reasoned from the code, not run).
- **So there is a new source of timing** in every test that disables a focused element and then yields. A `blur` and
  `focusout` can arrive on their own, into the app's `onBlur` handlers and into `Dialog.tsx:81-105`'s focus-return
  code. One green run per OS does not rule out a test that fails now and then; see decision C.
- **Under fake timers the focus check's interval is `vitest`'s to advance** (read: `jsdom` calls the global
  `setInterval`). An interval created under fake timers and never advanced stays recorded in `jsdom` after
  `vi.useRealTimers()`, and the focus check and `requestAnimationFrame`, which share it, then stop for the rest of that
  test file unless `cancelAnimationFrame` is called (for example after `Menu.test.tsx:370-375`). No file today has later
  tests that rely on either (read). It is a trap for a future test; step 7 puts it to the owner.
- **`window.reportError` is new,** and React 19 uses it when it exists; errors reach `vitest` the same way (reasoned).
- **Still missing in 31 (read):** `matchMedia`, `ResizeObserver`, `elementFromPoint`, pointer capture. The suite's
  stubs for them keep working.
