## Why they are held

- **#34 fails CI on Ubuntu** (run 39778208662), at *Tauri CLI pin matches package-lock.json* (`checks.yml:42-50`),
  after 6 s: it bumps `@tauri-apps/cli` 2.12.2 → 2.12.3, and `release.yml:165` still installs `tauri-cli --version
  2.12.2`. Windows and macOS are green; #34's Linux tests haven't run yet.
- **Either PR alone breaks `tauri build`.** #34 moves `@tauri-apps/plugin-clipboard-manager` to 2.5.0 and #35 moves
  the `tauri-plugin-clipboard-manager` crate to 2.5.0; `main` has 2.4.2 of both. `tauri build` refuses an npm package
  and its crate that differ in major or minor: `setup` runs the check (`tauri-cli-2.12.3/src/build.rs:115`,
  `:157-163` → `src/info/plugins.rs:39`, `:145`) before the `--no-bundle` branch (`:132`); 2.12.2 has the same check.
  So `main` with only one of them can't be built locally or released. Read from source, not run. CI doesn't run
  `tauri build`, so it can't see this.
- **#35 is green** (run 39778264055) but changes shipped runtime: the updater, single-instance, the opener, and how
  the Windows exe links its C runtime.

## Decisions

**D1. How they land — (b), the owner, 2026-10-23 (P1-1).** Every gate and walk runs on one tree: `main` with #35's
head, #34's head and the pin commit merged in. Then #35 and #34 are squash-merged back to back with nothing in between,
and `main`'s tree after the second merge must be identical to the walked tree. `main` is never left with one of them
alone. *Not taken:* (a) #35 first, leaving `main` unbuildable until #34; (c) one branch of our own, which closes both
PRs unmerged and loses Dependabot's PR history. (Neither option changes the release notes: `.github/release.yml`
leaves out the `dependencies` label, which both carry; pass 1's text said otherwise, P2-7.)

**D2. How each lands — as #32 did.** The pin commit onto #34's branch (`dff1e518`; #35 touches `Cargo.lock`, #34
`package*.json`, the pin `release.yml` `:160`/`:165`/`:230` beside #33's `:138`, so the merges are clean, simulated by
`git merge-tree`, and nothing needs a rebase), then each PR squash-merged with `--admin` (the owner's ruleset bypass)
and `--match-head-commit`, so a Dependabot push after the review can't be merged.

**D3. A Windows VM walk before the merges**, on the walk tree, ~60 min. Rows in step 5: the virtualizer rewrite
touches every list and the diff viewer.

**D4. A Linux VM check of #35's Linux changes — yes, the owner, 2026-10-23.** A second launch of the same build
(expected: it focuses the first window and exits) and *Reveal in folder* on a changed file, ~15 min. Only the normal
hand-off is exercised: the changed error paths (an instance that can't hand off, no session bus) aren't reachable this
way.

**D5. The dry run after the merges, from `main`, as #32's,** with the new installers read in the log. The owner,
2026-10-23: no RPM install on the Linux VM (the build log only); **yes** to a Windows reinstall (P1-4), into another
folder (P2-5 (b)): the dry run's `setup.exe` over the installed 0.10.24 on the Windows VM, *Uninstall T4 Git UI*
chosen on the reinstall page, another folder on the directory page; the old `%LOCALAPPDATA%\T4 Git UI` must then be
gone, which shows the new uninstall-in-place cleanup, and the app launches. It is the only check that runs the NSIS
3.13 installer, with `hooks.nsh`. Only the same-version page is covered (the dry run is also 0.10.24), not a manual
upgrade, where uninstall is the default. The released 0.10.24 is then put back at the default path (P2-4): the dry
run's build carries updater 2.14.0 under the same version number, and left installed it would void the first §AM
update walk.

**D6. `observeVisibleRect` — (a), the owner, 2026-10-23.** Kept; an `open-items.md` row to check and drop it.
**Reopen:** the next virtualizer work, or a walk showing virtual-core's default does the same. *Not taken:* (b)

**D7. The deferred row *A release run builds ssign and the Tauri CLI from source*** (`open-items.md:829`): its trigger
