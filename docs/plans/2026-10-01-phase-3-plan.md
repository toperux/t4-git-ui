## Corrections found while drafting

- **§A row 1's text is stale.** It says the walk runs "under the git2 mutex". It doesn't: `get_refs`
  (`src-tauri/src/commands/repo.rs:208-221`) opens a private `Repository` and takes only the `ahead_behind` cache lock,
  which nothing else takes. Only the sidebar's own refresh waits on it. Corrected in Stage B's docs commit either way.
- **E6 is O(n²) in sibling *folders*, not in a flat directory's files.** `buildFileTree` calls `children.find` only for
  path parts that aren't the last one (`fileTree.ts:24`), so N files in one folder are linear and N sibling folders are
  quadratic. `Sidebar.buildTree` calls `find` on every part, leaves included (`Sidebar.tsx:69`), so N refs in one folder
  (330 branches under one remote, ~1000 tags) are quadratic. Both sorts use `localeCompare`; whether that matters at
  these sizes is what row 6 measures.
- **The Files tab rebuilds its whole tree on every folder expand.** The `rows` memo (`ChangedFileList.tsx:83-93`)
  depends on `opened`, and calls `buildFileTree` over the full repository listing. On a 100k-file repo that is a full
  build and sort per click (reasoned; row 6a times it).
- **The commit panel's Changes lists rebuild their trees on every status refresh.** `FilesColumn.tsx:185` builds the
  tree from `entries`, which is re-split from each new status for the unstaged (`:87`) and staged (`:131`) lists.
  `ChangedFileList` serves the Files tab, commits, compare and stashes, not the working tree.
- **`canSquash` is quadratic only for a long squash / fixup run.** With every row a `pick`, `pickAbove`
  (`rebaseTodo.ts:41-45`) and `groupOf` (`:87-104`) return at once. A run of n fixups makes each row scan the run.
  `validate` (`:142`, `:146`) repeats it.
- **Row 8 has a timing line already.** `linked read` (`repo.rs:236`) logs every snapshot. It runs unawaited after each
  refs refresh (`src/store/repoStore.ts:383-390`), so it never holds the branch list. Its cost is a late worktree /
  submodule section of the sidebar.

## Rows

### 1. The merged-branch walk (§A `reachers`)

- **What the user sees:** after a commit, fetch, checkout or branch create/delete, the sidebar (branch list,
  ahead/behind counts, greyed merged branches) updates late. Nothing else waits on it.
- **Measured before:** ~400 ms on the old synthetic repo, 2026-09-07, older code.
- **Measure, on `perf-synth`, `perf-git`, A and B:**
  - the open: `opened repo`, `labels computed`, `walk complete`, `refs read`, `slow status` from the log (§A asks for
    these first); the tab closed between opens (untimed);
  - a commit in the app (before each, untimed: append a line to a file and stage it): `refs read`, the temporary walk
    line, and the action timer stamping the Commit click, the *Committed* toast, and the sidebar showing the new ahead
    count (A / B are given one in their scrub). Click → toast is the commit's own cost (`git commit` refreshing the
    index, `commitStore.ts:525-537`), recorded but not judged here; row 1 is judged on toast → sidebar painted as
    measured (mostly `refs read`, IPC and render). The refs refresh isn't gated on the status scan: the commit's own
    `repo://changed` event (`stage.rs:91-98`) starts it at once (`statusStore.ts:211`), beside a status fetch (`:167`),
    whether the event or the commit's reply lands first. The status line is recorded next to it as a parallel scan, not
    subtracted. A commit logs two `refs read` and walk lines (reasoned, not run): the event's refresh, then
    `commitStore.ts:537`'s own `syncRefs`, which re-runs it (`statusStore.ts:216-229`). Nothing moves between the two,
    so the second should hit both caches — the pairs and the merged result, keyed on the whole tip list
    (`refs.rs:400-401`) — and look like the cached case. The first pair after the click goes with the paint; the second
    is recorded as a cache hit (if its walk line is not near zero, that's noted for Stage B). A checkout behaves the
    same;
  - a remote-tracking tip moved from a terminal (`git update-ref refs/remotes/origin/<b> <older oid>`) — what a fetch
    does to the refs, without the network; the watcher's `Refs` event starts the refresh. A different `<older oid>` per
    repetition: the ahead / behind counts are cached per (local, upstream) pair for the life of the open repo
    (`refs.rs:218-227`), so a repeated pair costs nothing the second time;
  - **a stale local branch** (R4, `perf-synth`): `git update-ref refs/remotes/origin/maint main~1` (then `main~2` …
    `main~5` for the repetitions, for the same reason), so local `maint` (commit 10) is ~99,990 behind — a fetch that
    ran far ahead of a stale local. The walk's bound stays (local `maint` is still at commit 10). The ahead / behind
    share ≈ `refs read` − the temporary walk line − the cached case's `refs read` (it has no line of its own, and
    `refs read` also holds the private repository's open);
  - a checkout of another branch, alternating `main` ↔ `at-main-1` on `perf-synth` and `master` ↔ `at-master-1` on
    `perf-git` (each direction a sample), ending on `main` / `master` (a few commits apart, so the checkout stays cheap
    and the fixture stays as later rows need it);
  - the cached case: F5 with no tip moved.
- **After row 1** (untimed): `git update-ref refs/remotes/origin/maint maint`, and every moved `origin/<b>` back to its
  oid from before the move (on `perf-synth`, its local), so the pairs are as they were (else every later reopen pays a
  ~100k-commit ahead / behind walk inside the `refs read` that runs beside row 3's status scans).
- **Over if:** toast → sidebar painted after a commit, or `refs read` after a moved tip, is ≥ 250 ms (T2). `refs read`
  alone is a lower bound: the IPC and the sidebar's render come on top.

### 2. Hunk and line diff rebuilds (§A)

- **What the user sees:** each hunk or line stage, unstage or discard waits on rebuilding the whole file's diff
  (`max_lines: usize::MAX`, `stage.rs:359`) under the shared `git2` lock, so status and diffs queue behind it. For a
  path that is added or deleted, the rebuild also builds the whole-repository diff
  (`crates/git-core/src/diff.rs:388-391`); on the working-tree side that includes untracked files and their content
  (`:226-231`) and rename detection over them (`:262-267`).
- **Measure:**
  - **Modified file:** in `perf-git`, edit `sequencer.c` at 20 spread-out places, each edit a *replaced* line (a `-` and
    a `+`, so a staged single line leaves the other half unstaged). Stage the 20 hunks one by one: CDP click → hunk
    gone, plus the rebuild and total lines. Then `git restore --staged sequencer.c` (untimed), and stage 20 single lines
    the same way, each ending when that line is gone from its hunk (the hunk stays; a line action never ends on "hunk
    gone", here or below). (The buttons are disabled while one runs,
    `src/screens/RepoWindow/DiffViewer/DiffViewer.tsx:559`, `:563` for hunks, `:343`, `:347` for lines, so clicks can't
    pile up; no burst test.)
  - **Discard:** `git restore --staged sequencer.c` (untimed), then the 20 hunks discarded. A discard asks natively
    first (answered with `docs/smoke/fixtures/smoke-dialog.ps1`), so it's timed by the total line, not from the click.
  - **Added / deleted, staged side** (an added or deleted file is one hunk, so the line goes first): in `perf-synth`
    (100k files), stage a new 200-line file, then unstage one line, then the hunk; before each repetition, re-stage the
    whole file (untimed). Also a tracked file deleted and staged, then one line unstaged; before each repetition,
    `git rm --cached` it again (untimed) — after the unstage the index holds a one-line file, which is *Modified*, not
    *Deleted*, and would skip the whole-diff rebuild (`diff.rs:382-391`).
  - **Deleted, working-tree side:** in `perf-synth` with a few untracked files present, delete two tracked files (not
    staged); stage one line of the first, discard the hunk of the second. Before each repetition (untimed): unstage the
    first, delete the second again.
- **After row 2** (untimed): `git reset --hard` in `perf-git` and `perf-synth`, and the new 200-line file deleted, so
  row 3's touch-everything doesn't recreate deleted files as empty ones.
- **Over if:** one action is ≥ 250 ms.

### 3. Status at size (§Q `status.rs`)

- **What the user sees:** every watcher event re-scans status; a slow scan delays Changes after each edit.
- **Measured before:** 50 ms at 61k files (2026-09-07). The earlier 1.5 s case was a stale stat cache (each scan
  re-hashed every file), not size.
- **Measure:** `perf-synth` checked out with 100k files; A and B.
  - **Warm:** touch one file, read the status line.
  - **Stale:** close the repository's tab, touch every tracked file from a terminal
    (`git ls-files -z | xargs -0 touch`), reopen it. The open's first status line is the stale scan (re-hash plus
    write-back), the next one warm again. (With the tab open, the watcher would scan in batches during the touch, and no
    single scan would show the stale cost.) The same recipe on A and B.
- **Over if:** the warm scan is ≥ 250 ms. The stale case is recorded for the §Q row, not judged: it happens once after a
  mass touch, and the scan repairs the cache. If the warm scan is under, the §Q row stays with the numbers added; its
  reopen trigger (a real `slow status` line) is unchanged.

### 4. The output dock (§A)

- **What the user sees:** a long op's output is plain DOM, capped at 50 ops × 5000 lines
  (`src/store/opsStore.ts:12-13`).
- **The dock grows across repetitions** — it keeps every op of the session up to the cap (`opsStore.ts:12`, `:69`), and
  jumps to the bottom on every new line (`OutputDock.tsx:141-145`), so cost grows with its size. Rows 1–3 already put
  ops in it (row 1's commits and checkouts stream into it; row 2's stage ops don't, `stage.rs:386`). So the build is
  **restarted before row 4** (the ops store is in memory only), and each sample records the dock's op count (children of
  `[role=log]`) and line count (`[role=log] > div > div`: header, lines and exit rows).
- **Measure, in `perf-git` with the dock open,** through the in-app *Run git command…* dialog (Ctrl+Shift+R; it streams
  into the dock like any op, `src-tauri/src/commands/ops.rs:785`):
  - `paced` (the alias): the frame sampler while lines stream in (300 more lines per repetition, recorded);
  - `log -n 5000 --format=%H`: the sampler during the burst (runs 1–5, each 5000 lines bigger, recorded as such), then
    while scrolling the dock top to bottom (the sampler sets `scrollTop = 0` first);
  - the same scroll after 10 runs (runs 1–5 count toward them), and at the cap (50 runs, 250k lines kept), the runs
    driven by a CDP loop.
- **After row 4** (untimed): the build is restarted again, so rows 5–8 don't run beside a full dock (an open dock keeps
  its 250k rows mounted, `OutputDock.tsx:43-47`).
- **Over if:** jank by D3.

### 5. ~4 s after an external 1800-file `git reset` (§M)

- **What the user sees:** after a `git reset` of 1800 files in a terminal, Changes takes about 4 s to show it. An
  external `git add -A` of the same files shows in 0.6 s (`docs/archive/walks/2026-09-19-group-az-walk.md:65`). That
  walk's `git reset` was most likely a mixed reset (unstage all) after the `add -A`; inferred, not recorded.
- **Measure, in `perf-reset`, A and B:** with the 1800 files modified, `git add -u` from a terminal (the control; `-u`,
  not `-A`, so A's and B's untracked files stay out and both commands touch the same paths), then `git reset` (mixed),
  each with its end time printed in ms. A CDP poll every 16 ms reads the Changes bar's split counts ("N unstaged · M
  staged", `ChangesView.tsx:27`); the total badge can't see either command, since both move the same 1800 between staged
  and unstaged (`statusStore.ts:33-34`). The bar's unstaged figure includes untracked files (`ChangesView.tsx:23`), and
  A / B keep theirs (R1), so the end targets are read per repo from `git status --porcelain` before timing: `add -u` has
  landed when unstaged = the untracked count and staged = all modified tracked files; `reset` when staged = 0; the
  `--hard` variant below when the tracked changes are gone. The temporary watcher line logs each batch; with the status
  line, that splits the time into: the watcher's batches (the 250 ms debounce, `watch.rs:29`, and `classify` per event,
  `:101-131`), the status scans they start, and the render. The `add -u` / `reset` pair resets itself between
  repetitions. Then a variant (`perf-reset` only) that rewrites the working tree: once before it, `git stash` then
  `git stash apply` (the stash stays); timed, `git reset --hard` (Changes 1800 → 0); between repetitions, untimed,
  `git stash apply` and wait for Changes to settle.
- **Over if:** end of the reset → Changes updated is ≥ 250 ms more than the `add -u` control. The fix depends on which
  part is slow, so it is designed in Stage B.
