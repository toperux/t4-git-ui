## Corrections found while drafting

- **§A row 1's text is stale.** It says the walk runs "under the git2 mutex". It doesn't: `get_refs`
  (`src-tauri/src/commands/repo.rs:208-221`) opens a private `Repository` and takes only the `ahead_behind` cache lock,
  which nothing else takes. Only the sidebar's own refresh waits on it. Corrected in Stage B's docs commit either way.
- **E6 is O(n²) in sibling *folders*, not in a flat directory's files.** `buildFileTree` calls `children.find` only for
  path parts that aren't the last one (`fileTree.ts:24`), so N files in one folder are linear and N sibling folders are
  quadratic. `Sidebar.buildTree` calls `find` on every part, leaves included (`Sidebar.tsx:69`), so N refs in one folder
  (330 branches under one remote, ~1000 tags) are quadratic. Both sorts use `localeCompare`; whether that matters at
  these sizes is what row 6 measures.
- **The Files tab rebuilds its whole tree on every folder expand.** The `rows` memo (`ChangedFileList.tsx:83-93`)
  depends on `opened`, and calls `buildFileTree` over the full repository listing. On a 100k-file repo that is a full
  build and sort per click (reasoned; row 6a times it).
- **The commit panel's Changes lists rebuild their trees on every status refresh.** `FilesColumn.tsx:185` builds the
  tree from `entries`, which is re-split from each new status for the unstaged (`:87`) and staged (`:131`) lists.
  `ChangedFileList` serves the Files tab, commits, compare and stashes, not the working tree.
- **`canSquash` is quadratic only for a long squash / fixup run.** With every row a `pick`, `pickAbove`
  (`rebaseTodo.ts:41-45`) and `groupOf` (`:87-104`) return at once. A run of n fixups makes each row scan the run.
  `validate` (`:142`, `:146`) repeats it.
- **Row 8 has a timing line already.** `linked read` (`repo.rs:236`) logs every snapshot. It runs unawaited after each
  refs refresh (`src/store/repoStore.ts:383-390`), so it never holds the branch list. Its cost is a late worktree /
  submodule section of the sidebar.

## Rows

### 1. The merged-branch walk (§A `reachers`)

- **What the user sees:** after a commit, fetch, checkout or branch create/delete, the sidebar (branch list,
  ahead/behind counts, greyed merged branches) updates late. Nothing else waits on it.
- **Measured before:** ~400 ms on the old synthetic repo, 2026-09-07, older code.
- **Measure, on `perf-synth`, `perf-git`, A and B:**
  - the open: `opened repo`, `labels computed`, `walk complete`, `refs read`, `slow status` from the log (§A asks for
    these first); the tab closed between opens (untimed);
  - a commit in the app (before each, untimed: append a line to a file and stage it): `refs read`, the temporary walk
    line, and the action timer stamping the Commit click, the *Committed* toast, and the sidebar showing the new ahead
    count (A / B are given one in their scrub). Click → toast is the commit's own cost (`git commit` refreshing the
    index, `commitStore.ts:525-537`), recorded but not judged here; row 1 is judged on toast → sidebar painted as
    measured (mostly `refs read`, IPC and render). The refs refresh isn't gated on the status scan: the commit's own
    `repo://changed` event (`stage.rs:91-98`) starts it at once (`statusStore.ts:211`), beside a status fetch (`:167`),
    whether the event or the commit's reply lands first. The status line is recorded next to it as a parallel scan, not
    subtracted. A commit logs two `refs read` and walk lines (reasoned, not run): the event's refresh, then
    `commitStore.ts:537`'s own `syncRefs`, which re-runs it (`statusStore.ts:216-229`). Nothing moves between the two,
    so the second should hit both caches — the pairs and the merged result, keyed on the whole tip list
    (`refs.rs:400-401`) — and look like the cached case. The first pair after the click goes with the paint; the second
    is recorded as a cache hit (if its walk line is not near zero, that's noted for Stage B). A checkout behaves the
    same;
  - a remote-tracking tip moved from a terminal (`git update-ref refs/remotes/origin/<b> <older oid>`) — what a fetch
    does to the refs, without the network; the watcher's `Refs` event starts the refresh. A different `<older oid>` per
    repetition: the ahead / behind counts are cached per (local, upstream) pair for the life of the open repo
    (`refs.rs:218-227`), so a repeated pair costs nothing the second time;
  - **a stale local branch** (R4, `perf-synth`): `git update-ref refs/remotes/origin/maint main~1` (then `main~2` …
    `main~5` for the repetitions, for the same reason), so local `maint` (commit 10) is ~99,990 behind — a fetch that
    ran far ahead of a stale local. The walk's bound stays (local `maint` is still at commit 10). The ahead / behind
    share ≈ `refs read` − the temporary walk line − the cached case's `refs read` (it has no line of its own, and
    `refs read` also holds the private repository's open);
  - a checkout of another branch, alternating `main` ↔ `at-main-1` on `perf-synth` and `master` ↔ `at-master-1` on
    `perf-git` (each direction a sample), ending on `main` / `master` (a few commits apart, so the checkout stays cheap
    and the fixture stays as later rows need it);
  - the cached case: F5 with no tip moved.
- **After row 1** (untimed): `git update-ref refs/remotes/origin/maint maint`, and every moved `origin/<b>` back to its
  oid from before the move (on `perf-synth`, its local), so the pairs are as they were (else every later reopen pays a
  ~100k-commit ahead / behind walk inside the `refs read` that runs beside row 3's status scans).
- **Over if:** toast → sidebar painted after a commit, or `refs read` after a moved tip, is ≥ 250 ms (T2). `refs read`
  alone is a lower bound: the IPC and the sidebar's render come on top.

### 2. Hunk and line diff rebuilds (§A)

- **What the user sees:** each hunk or line stage, unstage or discard waits on rebuilding the whole file's diff
  (`max_lines: usize::MAX`, `stage.rs:359`) under the shared `git2` lock, so status and diffs queue behind it. For a
  path that is added or deleted, the rebuild also builds the whole-repository diff
  (`crates/git-core/src/diff.rs:388-391`); on the working-tree side that includes untracked files and their content
  (`:226-231`) and rename detection over them (`:262-267`).
- **Measure:**
  - **Modified file:** in `perf-git`, edit `sequencer.c` at 20 spread-out places, each edit a *replaced* line (a `-` and
    a `+`, so a staged single line leaves the other half unstaged). Stage the 20 hunks one by one: CDP click → hunk
    gone, plus the rebuild and total lines. Then `git restore --staged sequencer.c` (untimed), and stage 20 single lines

### Fix 1a — the upstream lookups (`refs.rs:645-674`)

- **Cause, measured:** `branch_upstream_name` and `Branch::upstream` cost ~1.7 ms each per local branch on
  `perf-synth` (332 branches, ~1.1 s together). Each call takes a fresh snapshot of the whole configuration, which
  holds a `branch.<name>` section per branch, so the cost grows with the square of the branch count (libgit2's
  `git_branch_upstream_name`, read by the review, not profiled). Each refresh pays it twice: `label_snapshot`
  (`commands/repo.rs:86`) and the refs read (`:216`) both run `collect`.
- **Fix:** one `repo.config()?.snapshot()?` per `collect`; per branch, `get_string("branch.<name>.remote")` and
  `("branch.<name>.merge")` from it — hashed lookups that keep libgit2's own rules (last value wins, includes, case,
  a dotted branch name like `release/1.2`). Then, as libgit2 does:
  - no remote or no merge key, or an empty value → no upstream;
  - remote `.` → the merge ref itself (a local upstream);
  - otherwise the remote (a remote → fetch refspecs map built once, before the local-branch loop — the existing
    `find_remote` at `:692-696` runs after it; a missing remote → no upstream, not "gone"): its fetch refspecs from
    `Remote::refspecs()`, push ones skipped, the first whose `src_matches` the merge ref, `transform`ed; no match →
    no upstream.
  - A remote with a negative fetch refspec (`src` starting with `^`), or one whose destination isn't under `refs/`
    (`+refs/heads/*:remotes/origin/*`): its branches use `repo.branch_upstream_name` as today. libgit2 gives no
    upstream when a negative refspec matches (`remote.c:2631-2649`, vendored 1.9.7, read by the review), and matches
    against refspecs it has rewritten to full `refs/remotes/…` names (`remote.c:560`, `refspec.c:425-436`), which
    `Remote::refspecs()` doesn't return; the slow path costs only on such remotes.
  - The upstream commit is `find_reference(upstream).peel_to_commit()`; a missing ref or a failed peel is "gone",
    as today.
- **Tests:** the new lookup against `branch_upstream_name` + `Branch::upstream` on: a remote upstream, a local one
  (`.`), a custom fetch refspec, a pruned remote branch ("gone"), no merge key, an empty value, a missing remote, a
  dotted branch name, a key set twice, a remote whose name contains a `/`, a remote with a negative fetch refspec
  matching the merge ref, and one with a destination outside `refs/`. The existing snapshot tests pass unchanged.

### Fix 1b — the merged walk, incremental (B1; `refs.rs:257-449`)

- **Today:** `cache.merged` is keyed by every tip's name, oid, HEAD flag and upstream (`:396-401`), so a checkout
  (the HEAD flag), a commit or a fetch (an oid) each throw it away and walk again — 0.5–0.7 s on the fixtures.
- **Fix:** split what the walk knows from what is derived from it.
  - Cache a reachability matrix over the *distinct tip oids*: `reach[a]` = the other tip oids `a` has as an ancestor
    (itself excluded). Tips sharing one oid reach each other, as today's `reachers` (`:245-246`): matched by oid when
    `merged_into` is derived. Names, the HEAD flag and upstreams are not in it; `merged_into` is derived from it on
    every call (the loop at `:414-434`, cheap). The full walk fills it from today's `reachers` over the distinct oids,
    transposed: `reachers`' `out[i]` (which tips reach tip `i`) is the matrix's *column* `i`, not its row.
  - On a new tip-oid set, the new oids are added **against the old matrix first**, and the oids no tip has any more
    are dropped after. (Dropping first would make a plain commit — `x` moves from `o` to `n`, nothing else on `o` —
    lose `o` as a boundary and fall back every time.) An oid already in the matrix costs nothing (a new branch on an
    existing commit, a push that moves `origin/x` onto `x`); a checkout changes no oid.
  - A new oid `n`: one `revwalk` from `n` with every cached oid hidden. If it yields nothing, `n` is reachable from a
    cached tip (a backward move, a reset): fall back to the full walk. Otherwise it yields the commits only `n`
    reaches; no cached tip reaches `n` (its column is empty), and its row is the union of `reach[p] ∪ {p}` over the
    boundary: the parents `p` of those commits that the walk didn't yield and that are cached oids.
  - A boundary parent `q` that isn't a cached oid (X1: a merged pull request's fork point) adds nothing when `q` is an
    ancestor of a cached boundary parent `p`: every tip `q` reaches, `p` reaches too. Checked for all such `q` at
    once with one more `revwalk` — every `q` pushed, every cached boundary parent hidden: it yields nothing when each
    `q` is covered (cheaper than a `graph_descendant_of` per pair; a false yield under clock skew only falls back).
    Otherwise (a branch from a commit no tip on the boundary reaches, an amend) it falls back.
  - Several new oids: one at a time, oldest commit first, each counting as cached for the next; one that an earlier
    one reaches yields nothing and falls back. More than 16 new oids (a fetch moving many branches) → one full walk
    instead of 16+ walks each hiding every tip.
  - Any `revwalk` / `find_commit` error (a dropped tip's commit pruned by `gc`) → the full walk, not an error.
- **Ceiling:** the full walk still runs for a backward move, a reset, an amend, a new branch or a fetched branch based
  on a commit no boundary tip reaches, and a fetch of more than 16 tips — a `ponytail:` comment and a §Q row. The
  commonest in the UI: the grid's *Create branch here…* and *Reset … to here…* on a non-tip row (a new oid that cached
  tips already reach, so the walk yields nothing); the §Q row names them.
- **Tests:**
  - A randomized test (fixed seeds) builds DAG histories with **non-decreasing commit times** (including runs in one
    second, for `children_first`), applies random moves — a new commit, a fast-forward, a backward move, an amend, a
    merge of two tips, a fetch-like batch bringing a merge whose side branch forks mid-history, batches of several
    tips and of more than 16, a new branch at an existing oid, a delete, a checkout — and asserts the incremental
    matrix and the full walk's both equal a brute-force one (`graph_descendant_of`) after each.
  - A walk counter on the cache: a checkout, a commit, a fast-forward onto new commits (not onto a commit another tip
    reaches, which falls back by design) and the merged-PR batch don't run the full walk (otherwise the fallback would
    make the equality hold trivially).
  - The existing `merged_into` tests pass unchanged.
- **Known difference:** on a history with clock skew (a commit stamped older than its parent — git/git has some),
  the full walk can lose reachers (`:252-256`), and libgit2's hiding walk also leans on dates (reasoned), so the two
  paths can differ there. BL 1 compares badges only on `perf-synth` (no skew).

### Fix 5 — one scan at a time (`commands/diff.rs:79-107`)

- **Cause, measured:** each watcher batch starts another scan while earlier ones still run: 7–10 at once on
  `reset --hard`, all finishing together 4.6–6.2 s after the reset. The frontend's sequence check (`statusStore.ts:147`)
  drops old answers but not the scans.
- **Fix:** per handle, a scan gate (`tokio::sync::Mutex`, fair) holding the start number and `Arc` result of the last
  finished scan, and a request counter (the command returns the `Arc`: the workspace's serde gains the `rc` feature,
  `Cargo.toml:10`, rather than cloning a ~10 MB status per waiter). A request takes the next number, then waits for the
  gate. If the last finished scan started after the request, it gets that result; otherwise it checks T7's token (added
  with T7, in the next commit) and runs a scan, which counts for every request numbered before it started. So one scan
  runs, at most one more is queued, and no caller gets a status older than its request. Errors are not shared. While the
  scan is still libgit2's (this commit lands before fix 3), the gate holder takes `scan_lock.try_lock()` and the
  `refresh` flag when its scan starts, not before waiting (`commands/diff.rs:95` today): a queued request holding it
  would make an op wait behind a scan that hasn't started.
- **L8 — non-UTF-8 paths keep their counts:** the status reads paths lossily (a file on disk only on Linux, since
  Windows file names are always valid UTF-8; an index entry on any OS — the map and the swap are not OS-gated, only the
  test is), so a list entry made from one would match no file. The scan result carries a backend-only map, lossy path →
  raw bytes (`#[serde(skip)]`), for the paths that weren't valid UTF-8 (filled from `path_bytes()` until fix 3, from the
  porcelain bytes after). The gate holder also stores each finished `Arc` in a non-waiting slot on the handle
  (`parking_lot::Mutex<Option<Arc<…>>>`) — the gate's own mutex is held for a whole scan, ~6 s stale, which a read would
  wait out. `get_changed_files` (`src-tauri/src/commands/diff.rs:18-25`, which holds the handle) reads the slot only
  when a listed path holds U+FFFD and swaps each one found for its raw bytes through a git-core helper, before calling
  `changed_files` with the byte list (fix 2's signature, so no other call site changes); the deltas come back under the
  same lossy key the status entry has (`diff.rs:271-273`). A path missing from it (no scan finished on this handle yet,
  or a newer scan dropped it) goes in as its lossy bytes and gets no counts until the next sync, as today. A git-core
  test in `tests/diff.rs` (`cfg(target_os = "linux")`; it needs no git until fix 3, which puts it under the file's new
  `have_git()` guard with the other status callers; the test uses a file named with the Latin-1 bytes `b"caf\xe9.txt"`,
  through `OsStr::from_bytes`, committed then modified) drives status → map → the helper's swap → `changed_files` and
  gets its counts; the slot read itself is the command's two lines. Its file diff still fails (`diff.rs:347-351`).
- **Tests:** eight concurrent requests run at most two scans (a counting scan function), and a request made during
  a scan gets a later one.
