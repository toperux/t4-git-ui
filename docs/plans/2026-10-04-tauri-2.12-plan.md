### The bundler: tauri-cli 2.12.1 locks `tauri-bundler` 2.10.1 (2.11.5 locked 2.9.4)

**AppImage tools** (`src/bundle/linux/appimage/linuxdeploy.rs`):
- **linuxdeploy** moves to a fixed build: the file `linuxdeploy-07333c6-x86_64.AppImage`, downloaded from
  `…/binary-releases/releases/download/linuxdeploy-07333c6/linuxdeploy-x86_64.AppImage`. The old pin is
  `linuxdeploy-x86_64.AppImage`, from the moving `linuxdeploy` tag. sha256
  `36a2d7e274d12e1050d0e9ecfe11d339ed54720b2bec464c286d53f8b07f5c62`: measured on two downloads, and equal to GitHub's
  own asset digest (published 2026-09-20).
- **The gtk and gstreamer plugin scripts are embedded** (`include_bytes!`) and rewritten into the tool cache whenever
  the cached copy differs (`linuxdeploy.rs:230-246`). The pinned downloads in `release.yml` would be overwritten every
  run. The scripts are now pinned by the CLI version itself, through the crates.io checksum under `--locked`.
- **AppRun** (`apprun-old`) and **linuxdeploy-plugin-appimage** (`continuous`, which `release.yml` pins to
  `1-alpha-20250213-1`) are unchanged. The runtime (`LDAI_RUNTIME_FILE`) is ours and unchanged.
- **`bundleXdgOpen` is gone.** The app never set it, and inside an AppImage it opens files through the host's
  `xdg-open` (`commands/repo.rs:433`), so nothing changes for it.

**linuxdeploy `07333c6` excludes `libwayland-client.so.0` itself.** The review passes unpacked both builds: `07333c6`'s
exclude list adds two names, `libwayland-client.so.0` and `libpipewire-0.3.so.0` (0.10.18's AppImage bundles no
libpipewire, so the second changes nothing here). So `release.yml`'s *Remove libwayland-client from
the AppImage* step would find nothing to remove, and `appimage-strip.sh:53-54` exits 1. That step's own comment
(`release.yml:363-371`) and the release skill (`SKILL.md:166-168`) already say what to do then: drop the repack and
the re-sign. Ruled N2.

**The new gtk script no longer forces X11.** The pinned script (`dda522b`, line 246) has `export GDK_BACKEND=x11`,
with a link to tauri#8541, a crash on Wayland; 0.10.18's AppImage exports it unconditionally (its
`apprun-hooks/linuxdeploy-plugin-gtk.sh:17`). The embedded script has the line commented out ("Monitor this closely.
AppImage used to crash on Wayland!"). So on a Wayland desktop the next AppImage would run native Wayland, where the
app's window positioning (the tear-off placement, `window.rs:299-303`, and window-state's restore) is ignored. That
fires `open-items.md` §Q's reopen trigger on the row *AppImage always under XWayland*. Ruled N1: keep X11, always.
The script's other changes:
- **GIO modules.** The old hook copied only `libgiognutls.so` and set `GIO_EXTRA_MODULES`, which adds to the host's
  module directory (`dda522b:381-389`). The new one copies the build host's whole `giomoduledir`, runs
  `gio-querymodules`, and sets `GIO_MODULE_DIR`, which *replaces* the host's (embedded script `:266-278`). 0.10.18's
  AppImage holds only `libgiognutls.so` there (measured). So the next one may also bundle Ubuntu 22.04's (jammy's)
  libproxy, dconf and gvfs modules, and stop loading the host's (reasoned): a risk to GSettings and the file chooser's
  mounts, of the same kind as the bundled `libwayland-client` was. It may also end `open-items.md` §V's *The AppImage's
  bundled GLib can't load the host's GIO modules* (the gate's `libgvfsdbus.so` warnings), since bundled modules match
  the bundled GLib (reasoned). Checked in Verify. Child processes are fine: `GIO_MODULE_DIR` points under the AppImage's
  mount, which `host_env` removes (`crates/git-core/src/lib.rs:142-170`);
- a pixbuf guard, and documentation URLs.
- Its `dpkg-architecture` exit was already in `dda522b`. `build-essential`, which `release.yml:132` installs, depends
  on `dpkg-dev`, which ships the tool (packages.ubuntu.com, Ubuntu 22.04).

**The Windows installer's running-app check now uses Restart Manager.** Bundler 2.10.1's `CheckIfAppIsRunning`
(`nsis/utils.nsh:24-37`) takes a full executable path, and `installer.nsi:646, 783` pass
`"$INSTDIR\${MAINBINARYNAME}.exe"`. Our pre-install hook (`src-tauri/windows/hooks.nsh:9`) passes the bare file name,
so a running copy of 0.10.8 or older (installed under the old name) would likely go undetected and be closed by its
uninstaller without asking (reasoned: `installer.nsi:640` runs `SetOutPath $INSTDIR` just before the hook, so a bare
name would resolve against the new install folder).
Ruled N3: pass the full path, and walk it.

The rest of the bundler diff is formatting (the deb, rpm and macOS bundlers, `windows/sign.rs`, `bundle.rs`'s updater
artifacts), plus an opt-in VC-runtime bundling for Windows (`bundle_vc_runtime`, off by default; the app doesn't set
it). `tauri bundle` still binds `version:` into every updater signature (`tauri-cli bundle.rs:312`),
and `signer sign` still takes `--app-version` (`signer/sign.rs:47`).

### The plugins

**Updater 2.12.0 → 2.13.1.** The `src/` diff is refactors (edition 2024 `let`-chains), doc comments, and one
behaviour change. On Linux, `check()` used to set `SSL_CERT_FILE` / `SSL_CERT_DIR` to Debian paths when they were
unset (`updater.rs:439-448` in 2.12.0); 2.13 doesn't.
- On a Debian-family host nothing changes: the paths existed. The exposure is non-Debian distributions, which nobody
  walks.
- Child processes (git, tools) used to inherit those two variables after an update check; `host_env` keeps them. Their
  absence is reasoned to be harmless or better.
- `verify_signed_version` (`updater.rs:1666`) is unchanged, so `requireSignedVersion` behaves as before. Both versions
  use rustls.

**window-state 2.5.0, single-instance 2.5.2:** formatting and `let`-chains (window-state's match-guard refactor
behaves the same), a smaller global API script (the app doesn't set `withGlobalTauri`), MSRV 1.90, `windows-sys`
0.61. **opener 2.7, dialog 2.8, clipboard 2.4, store 2.5:** no API or permission change that the app uses; the
permission directories are identical. opener's `Error::Win32Error` wraps a newer `windows` type, which the app doesn't
use.

### tauri, tao and wry

From the release notes, the items that touch this app:
- **tauri 2.12.0:**
  - monitor queries (`monitor_from_point`, `available_monitors`) now run on the main thread. The tear-off clamp's
    `screen_at` already calls them there (`window.rs:155`), and they run inline then (runtime-wry `lib.rs:263-273`),
    so no deadlock;
  - channel payloads and large invoke responses are bound to their webview and purged when it closes (a security
    fix, GHSA-w28w-mhc8-qvjv). Listeners are removed when their window closes. Both touch the multi-window paths;
  - the ACL scopes `deny` permissions to their capability: the app has none;
  - MSRV 1.90. Local Rust is 1.99, CI uses `stable`; the VMs' and the Mac's toolchains are checked before their
    builds.
- **tao 0.36 / 0.37:**
  - 0.37.0, Windows: a hidden window's maximize is delayed, and its size and position reads change. The app builds
    windows hidden and reads their sizes (`window.rs:158-170, 281`);
  - 0.37.0, Windows: `WM_ENDSESSION` (what the installer's Restart Manager shutdown sends) now exits the process. tao
    calls `loop_destroyed()` first (`event_loop.rs:2336`), which becomes `RunEvent::Exit`; window-state saves on `Exit`
    (tauri-plugin-window-state 2.5.0, `lib.rs:528-529`). The app's own `Exit` arm (`src-tauri/src/lib.rs:304`) only
    clears the restore mark (`window.rs:429-440`); the layout is kept because no window fires `Destroyed`, so
    `layout.json` keeps what it holds (measured in the sources; BO 8 checks it);
  - 0.37.1: `set_visible` focuses a window built with `with_focused(false)`. The app sets no such flag;
  - 0.36.0: Wayland decoration changes.
- **wry 0.57:** nothing beyond the items above was found that the app touches.

## Decisions

**Ruled 2026-10-04:**
- **N1 — keep the AppImage on X11, always** (scope ruled after review pass 2: a user's own `GDK_BACKEND` doesn't
  win, as before). The app sets it itself (Step 3). Native Wayland for the AppImage would be its own change.
- **N2 — drop the repack and the re-sign** (Step 5), as the pipeline's own comment says to.
- **N3 — the full path in `hooks.nsh`, and walk it** (Step 4, BO 9).

**Ruled 2026-10-05, all as recommended:** D1 (a) the latest patches, D2 (a) by hand on one branch, D3 (a) drop the gtk
and gstreamer pins, D4 (b) the dry run on `main`, D5 (a) the VMs plus the Mac subset, D6 (a) accept, D7 (b) the AppDir
check. The context each was ruled on stays below. Shorthand used: *BO*, *BN*, *BC* and *BJ* are smoke groups in
`smoke-test-post-v1.md` (BO: this plan's, under Verify; BN: Phase 5's menus and tear-off; BC: the T4 Git UI rename's
installer; BJ: Phase 1b's local update test); *the dry run* is a `workflow_dispatch` of `release.yml`, which builds,
signs and rehearses the publish without releasing; *MSRV* is a crate's minimum supported Rust version.

- **D1 — which versions.**
  - *What:* Dependabot proposed CLI and API 2.12.0, `plugin-dialog` npm 2.8.0 and clipboard npm 2.4.0; 2.12.1, 2.8.1
    and 2.4.1 are out. *Why now:* the branch has to pick one.
  - (a) The latest patches everywhere: every crate/npm pair on the same patch, and 2.12.1's fixes (its CLI changes
    are a template tweak and the bundler 2.10.1 bump). (b) Exactly #19 and #20: crate 2.12.1 against npm 2.12.0
    (allowed by the minor-only check), and next week's Dependabot PR brings the rest. Cost: the CLI pin becomes
    2.12.0, which locks bundler 2.10.0, a version this plan never read (its AppImage tool pins and NSIS changes
    could differ from 2.10.1's), so the bundler review would have to be redone.
  - *Known:* the versions and the check's rule (measured). *Not known:* nothing found that 2.12.1 breaks.
  - **Recommend (a):** it's what Dependabot proposes next week anyway, so taking it now saves a second walk for one
    patch, and every pair matches exactly.
- **D2 — how it lands.**
  - *What:* the two PRs can't merge separately: #20 alone breaks `cargo tauri build` (the version check), and #19
    alone fails the CI guard. *Why now:* it decides the branch's shape.
  - (a) By hand on one branch. Dependabot then closes #19 and #20 itself once `main` carries their versions
    (reasoned from its usual handling of superseded PRs); if it doesn't, they're closed with a comment, on the
    owner's word. (b) Both PR branches merged together into one branch: the same result with the PRs' history, but
    #19's lockfile has 2.12.0 and needs redoing for D1 (a) anyway.
  - *Known:* #20 changed only `Cargo.lock`, #19 `package.json` and its lock (measured). *Not known:* whether
    Dependabot closes both by itself: it compares versions, and with D1 (a) `main` is ahead of both, which it usually
    treats as superseded (reasoned). A floor left lower than #19's would make it re-propose, which Step 1 avoids.
  - **Recommend (a):** one change, one review, one walk, and the history on `main` reads as one bump.
- **D3 — the gtk and gstreamer pins** (a separate step from N2's repack).
  - *What:* `release.yml` downloads the two plugin scripts at pinned commits and checks their hashes. Bundler 2.10.1
    carries its own copies and writes them over any cached file that differs. *Why now:* the pin step is edited
    anyway for linuxdeploy.
  - (a) Drop them. Risk: none found; what runs is pinned by the CLI's crates.io checksum. (b) Keep the fetches: two
    downloads that can still fail a build (a GitHub outage) while deciding nothing.
  - *Known:* the overwrite (measured, `linuxdeploy.rs:230-246`). *Not known:* nothing open.
  - **Recommend (a):** a pin that controls nothing reads as protection it doesn't give.
- **D4 — where the dry run runs.**
  - *What:* the dry run needs the `signing` environment, which allows only `main` and `v*` tags. *Why now:* it decides
    the push order.
  - (a) Push the branch, add it to the environment for the run and remove it after (the procedure the close-out plan's
    Phase 1b used, the signing setup of 2026-10-01), dispatch from it, then fast-forward `main`. Three extra outward
    steps: the environment change, its removal, and a `workflow_dispatch` of `ci.yml` on the branch (`ci.yml:22`; pushes
    run it only on `main`). `main` only ever gets a proven pipeline.
  - (b) Push to `main` after the local gates and walks, dispatch on `main`, tag only once it's green. Fewer steps, and
    the push runs `ci.yml` on all three OS first. If the dry run fails, `main`'s release pipeline is broken until a
    fix lands, with no release pending meanwhile.
  - *Known:* the environment's rules and `ci.yml`'s triggers (measured). *Not known:* whether the dry run passes; the
    pipeline changes (N2, the pins, D7) are only proven by running it. Under (b) the release AppImage's own checks
    (the GIO modules as built on 22.04, the listing diff) are also first seen after `main` has the change; BO 10
    walks N1 and the new gtk hook on a local AppImage before the push either way.
  - **Recommend (b):** nothing is released from `main` without a tag, so a red dry run there costs a fix commit and
    nothing else, while (a) adds an environment change, its removal, and a CI dispatch on the branch.
- **D5 — how much to walk.**
  - *What:* unit tests and CI don't reach tear-off, restore, single-instance, the installer or the updater, and those
    are what the bump moves. *Why now:* the walks are booked on the VMs and the Mac before the go.
  - (a) BO on both VMs, and BO 1, 2, 6 and 7 on the Mac (the Mac's own window code and the WKWebView). Cost: about 2–3
    hours of VM and Mac time; the Mac walk runs on the owner's desktop, and the owner checks the Linux folder picker
    by hand twice (BO 10 and the dry run's AppImage), a few minutes each. (b) The VMs only: a macOS-only window or
    focus regression (tao's macOS code moved too) would first show at the release gate, or to users. (c) CI, the dry
    run and the release gate only: a tear-off, restore or installer regression would ship and be found by users.
  - *Known:* which crates moved and their notes (measured). *Not known:* whether any of it changes behaviour here;
    that is what the walk answers.
  - **Recommend (a):** these are exactly the paths Phase 5 just fixed and walked on all three OS, and a regression in
    them reaches every user on the next update.
- **D6 — updater 2.13's install path.**
  - *What:* the v0.10.19 gate updates 0.10.18 with its old updater (2.12). 2.13 installs an update for the first time
    at the release after. *Why now:* (b) would have to run before the release, so it's planned now or not at all.
  - *The cost that shows later:* if 2.13's install path were broken, every installed 0.10.19 would be stranded: it
    could check for updates but not install one, and users would have to download the next release by hand. Nobody
    would know until the 0.10.20 gate.
  - (a) Accept that: the measured diff of the install path is refactors only (`let`-chains); the one behaviour change
    is the Linux certificate variables, which BO 6 covers on a Debian-family host. Risk: the stranding above, judged
    unlikely from the diff. (b) A local update test now (a local endpoint serving a newer build, as group BJ did):
    about an hour per OS, and it proves 2.13 installs before anyone runs it.
  - *Known:* the source diff (measured). *Not known:* how 2.13 behaves on a real install, until (b) or the next gate.
  - **Recommend (a):** the install-path diff is mechanical, and the stranding has a manual way out (the download
    page); (b) costs about three hours for a path the diff shows unchanged.
- **D7 — a guard against `libwayland-client` coming back** (found while folding in N2).
  - *What:* the repack's last check also proved the library was gone. With the repack dropped, nothing would notice a
    future linuxdeploy that bundles it again, and the AppImage would open blank on newer hosts again (0.10.12's bug,
    fixed in 0.10.13). *Why now:* N2 removes the only check.
  - (a) List the built image (`unsquashfs -l -o <offset>`, the offset from python3 as in `appimage-strip.sh:31-40`)
    and fail if the library is in it. Keeps squashfs-tools and its 1:4.5 floor; about 10 lines.
  - (b) Test the AppDir the bundler leaves beside the image (`T4 Git UI.AppDir`; the bundler deletes only its deb
    staging, `linuxdeploy.rs:203`, and `release.yml:372` says so; *Clear stale bundle output*, `:173-175`, makes it
    fresh every run): fail if the AppDir is missing, or if `find "<AppDir>" -name 'libwayland-client*'` finds
    anything (the whole tree, as the old script's last check grepped the whole listing). Two lines, no
    squashfs-tools. Risk: it checks what was squashed, not the image itself (reasoned to be the same).
  - (c) No check: rely on linuxdeploy's exclude list and the release gate's Linux walk. Cost: the gate walks the
    already-published release, so a library that came back would reach users before the gate saw it.
  - *Known:* the AppDir is left in place (measured). *Not known:* whether a future bundler keeps leaving it; (b)'s
    missing-folder check turns that into a red run rather than a silent pass.
  - **Recommend (b):** the same protection as (a) for two lines, and it lets the squashfs-tools install and its floor
    go.

## How it runs (`CLAUDE.md`)

1. This plan's review loop, decisions asked as they come up.
2. On the owner's go: the branch, Steps 1–7, the local gates, each step committed locally.
3. The change review loop, then BO's walks (each machine's store backed up first, restored after).
4. Triage, one item at a time with the owner.
5. Squash, rehearsed in a throwaway worktree. Then ask before each of: the push (D4), the dry run.
6. The dry run's checks and its AppImage on the Linux VM (Verify). A finding there goes back through fix → change
   review → triage before any tag.
7. Ask before the release of v0.10.19, then its gate.

## Risks

- A tear-off, restore, maximize or single-instance regression from the crate bumps that only a walk shows: BO 1–3.
- The installer closing the running app without its state saved (tao 0.37's `WM_ENDSESSION` exit; the sources say it
  saves): BO 8.
- The AppImage bundling Ubuntu 22.04's GIO modules in place of the host's: the dry run AppImage's listing diff and file
  dialog.
- The AppImage built differently by linuxdeploy `07333c6`: the dry run's AppImage walk and the gate's update walk.
- TLS roots for the update check on non-Debian distributions, which nobody walks (D6 (b) wouldn't cover them
  either: it runs on the same Debian-family VM): proposed to the owner for acceptance at triage (How it runs, step
  4), with the reopen trigger *a report of a failing update check from a non-Debian distribution*.
- CI no longer digests the built AppImage (the strip script's `--check` goes with it, Step 5); the gate's Linux walk
  still checks the published one: proposed to the owner for acceptance at triage, like the TLS-roots item.
- Updater 2.13's install path unproven until the v0.10.20 gate: a broken one strands every 0.10.19 install, with the
  manual download as the way out. Accepted (D6 (a), 2026-10-05); recorded as a §Q row (Step 7).
