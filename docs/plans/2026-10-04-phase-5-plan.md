## Decisions (taken 2026-10-04; D6–D11 during execution)

- **D1 — tab adoption on macOS: accepted as a limit.** On macOS (and Linux), a tab dropped on another window's tab
  strip opens in a new window instead of moving there; a window's only tab dropped on another window does nothing
  (smoke `:1659`, `:1669-1670`). The way round is two steps: close the tab, then open the repository from Recents in
  the other window (opening a repository open elsewhere only brings that window forward, smoke `:1650-1651`). Rejected:
  building `window_at` on macOS (`objc2` / `objc2-app-kit`, already in `Cargo.lock`) and on X11 (`x11rb`, likewise) —
  native code with Cocoa's bottom-left, point-scaled coordinates that only a Mac walk could prove. Goes to open-items
  §Q with the reopen trigger "a macOS or X11 user asks to drag a tab into another window". M1 still drags a tab and
  records what happens.
- **D2 — the update walk on the owner's install: walk it, first.** The owner's 0.10.12 becomes 0.10.17.
- **D3 — Option+digit stays the view switch.** The M4 fix leaves digit keys out (below).
- **D4 — the fix reaches the Mac on a pushed side branch** `phase-5`, as `phase-3b` did for BL 11; pushed on the
  owner's go at that moment, deleted after.
- **D5 — mouse input on the Mac: `cliclick`** (Homebrew), installed on the owner's Mac for right-clicks, drags and
  hover; System Events alone sends keys and left-clicks only.
- **D6 — T12: one rule for all menus** (taken 2026-10-04, after the Windows control run). Path (b) marked the
  submenu's first row on WebView2 too, so T12 isn't WebKit's: `openedByKey()` counted an opener that still carries
  the mark as a keyboard open, a rule `7dcf7ff` copied from Chromium's own `:focus-visible` chain. Context menus
  already dropped it (Phase 2b D5); dropdowns and submenus now drop it as well — every menu asks `lastInputWasKey()`
  alone, as native menus do. This reverses Phase 2b D5's "the dropdown keeps its opener rule": a toolbar button
  reached with Tab and then clicked opens unmarked; Enter, Space, Shift+F10 and the arrows still mark. Rejected: the
  submenu alone (leaves dropdowns inconsistent), accepting it as designed.
- **D7 — a select opened by a click focuses itself** (taken 2026-10-04 from M1's walk: on macOS its keys were dead
  and it didn't close on an outside click, as WebKit gives a clicked button no focus). `Input.tsx`'s trigger calls
  `focus({ preventScroll: true })` in its click handler, and its mousedown is prevented so WebKit doesn't blur (and
  close) an open list just before the click; smoke BN 5.
- **D8 — "Ctrl+" shortcut hints on macOS: deferred** to an open-items row with its own plan (~72 hard-coded hints in
  17 files: menus, the palette, tooltips, the start screen); fixing menus alone would mix Ctrl and ⌘ labels.
- **D9 — M3 path (b) on macOS** lost focus to `<body>` (the submenu open, nothing focused, ↓ dead): measured again in
  the BN re-walk on the fixed build, with the focus and mouse events logged, before any fix is decided.
- **D10 — a click, → or Enter on a submenu row whose panel the hover opened takes the focus in** (taken 2026-10-04
  from D9's measurements). The owner's real-mouse check failed 15 of 15: a hand rests on the row past the 150 ms
  hover grace, so the panel is open before the click; the click's `setOpenSub` changed nothing, the focus effect
  didn't run, and on macOS the press had already dropped focus to `<body>` — the keyboard stranded until Escape.
  `openPanel` now focuses the first row itself when the panel is already open (marked only after a key, per D6).
  The same no-op hit → / Enter after a hover on every OS (reasoned). Smoke BN 6, by hand.
- **D11 — the submenu's "take the focus" flag is spent once used** (taken 2026-10-04 from change review pass 7; the
  bug predates Phase 5). `takeFocus` was set by a click or key and never cleared, so a later reopen by hover pulled
  the focus into the panel. The open/close effect now clears it. Smoke BN 6's last sentence.

### M6 — the macOS update walk (first)

The Mac has T4 Git UI **0.10.12** installed (self-signed, `dev.topher.t4gitui`). No macOS update has ever been
walked. Updating it in place to 0.10.17 checks the `.app.tar.gz` and its `.sig`, the restart, and that the signing
identity carried over (macOS keys Documents / Desktop / Downloads access to it). It does **not** check
`requireSignedVersion`: that is the installed app's setting, and 0.10.12 predates it (first shipped in 0.10.15). After
this walk the Mac is on 0.10.17, so a macOS half at the next release gate would be that setting's first macOS check.
0.10.12 → 0.10.17 is one hop: 0.10.12's updater (2.11.0) already accepted a version-carrying `.sig` in the 0.10.12 →
0.10.13 walk (Windows; macOS reasoned the same **(R)**).

Steps: back up `~/Library/Application Support/dev.topher.t4gitui`; `codesign -d -r-` on the installed app (the
designated requirement, which `release.yml` checks); launch it; badge → Settings → *Update to 0.10.17…*; record each
UI stage with its time (the updater writes nothing to the app log, open-items §B), the restart (old pid gone, new pid,
not started by hand), `CFBundleShortVersionString` = 0.10.17, `codesign -d -r-` again (the same requirement); open a
recent repository under Documents / Desktop / Downloads if one exists (no new access prompt); Settings › Check now →
up to date; quit; restore the store.

### M3 — T12

A menu opened by a pointer must not mark its first item; one opened by a key must. Before D6, a submenu marked its first
row when `openedByKey()` held (`Menu.tsx:85-88` at `ac8ecac`), which includes a focused opener that carries `data-kbd`
(the Linux plan's `:49`). T12's worry: WKWebView doesn't move focus on a click, so a parent row marked by the arrow keys
and then **clicked** stays focused and marked, and its submenu opens marked **(R)**. Context menus have no submenus; the
Repository menu's **More recent** is one, shown with more than five other recents (`Toolbar.tsx:59`, `:243-246`).

Seed six or more other recents in `recents.json`, then three paths:
- **(a) click, click:** click the repository-name button, click **More recent** → no highlight (the baseline).
- **(b) the T12 case:** open the menu, ↓ until **More recent** is focused (marked), then click it → expected: no
  highlight; a highlight is T12 confirmed.
- **(c) keys:** ↓ to **More recent**, → → the submenu's first row is highlighted.

Each click is one `cliclick c:x,y`, with no `m:` move first: a pointer resting ≥ 150 ms on **More recent** opens the
panel by hover without focusing anything (`SUBMENU_HOVER_MS`, `Menu.tsx:44`, `:254-257`; the focus effect runs only
when `open` changes, `:380-383`), which would pass (b) for the wrong reason. A screenshot can't tell "focused,
unmarked" from "nothing focused", so each path reads `document.activeElement` and its `data-kbd` through the
instrumentation (Order step 3): a 100 ms poll writes the active element's text and its `data-kbd` into the native
title, read once the click has settled (a `focusin`-time read would miss it: `focusItem` sets `data-kbd` after
`focus()`, `Menu.tsx:76-77`). The same can happen in Chromium (a click on the focused button fires no
`focusin`, so `data-kbd` stays) **(R)**: path (b) is also run on Windows over CDP, so a fail is put down to the right
engine. A fail is a finding, triaged.

### M4 — Option-typed type-ahead

**The problem.** In a select (the app's own `Input.tsx` combobox: Settings › Diff & merge's tool pickers, the
toolbar's branch filter, the commit panel), a letter typed with Option held (å, ø) should search the options like any
letter. Today it does nothing: Option arrives as `altKey` without `ctrlKey`, so `Input.tsx:206-207` takes it for an
Alt chord and returns **(R)**. Phase 2a let only AltGr (Ctrl+Alt on Windows) through.

**Measure first**, on today's build: what `key`, `code` and `altKey` a focused select receives for Option+a, Option+1,
Option+↓, and Option+u then u (a dead key). The trigger is a `<button>`, so no composition runs there; the dead key's
second keystroke carries no `altKey`, so the fix can't change it — the measurement says whether it works today. Keys
reach the select only with keyboard focus (a click doesn't focus a button in WKWebView): Tab with macOS *Keyboard
navigation* on, or Option+Tab; recorded which. The reading comes from temporary instrumentation in the scratch build
(Order step 3: the keydown's fields written into the native title, read through System Events), not the Web
Inspector, which needs a person at the console.

**The fix, if the measurement agrees** (a few lines plus tests): on macOS, an Alt keydown whose `key` is one character
and whose `code` is not a digit is type-ahead, not a chord:
`const altChar = e.altKey && e.key.length === 1 && (e.ctrlKey || (isMac() && !/^Digit/.test(e.code)))`, replacing
`altGr` at `:206`, `:207` and `:227` (`:227`'s `!e.ctrlKey` already lets Option-without-Ctrl through). `isMac()` goes
in `src/lib/keys.ts` beside `ctrlOrCmd`, read per call so tests can stub the user agent
(`vi.spyOn(navigator, "userAgent", "get")`, as `StartScreen.test.tsx:118`). Option+↓ / Option+↑ keep their meaning
(`key` is an arrow). Why the digits stay out (D3): the type-ahead branch calls `preventDefault` (`:228`), and the
window's shortcut handler skips a prevented event (`useShortcuts.ts:37`), so a focused select outside a dialog (the
branch filter, the commit panel, the search popover) would swallow Option+1 / Option+2's view switch. Option+Space
(U+00A0) becomes a type-ahead character too: harmless, it matches nothing.

**Tests** (`Input.test.tsx`): with a Mac user agent, Option+å (`code: "KeyA"`) moves the active option; Option+↓
still opens; Option+1 (`key: "¡"`, `code: "Digit1"`) is not prevented (the event reaches the window). Without it
(Windows, no Ctrl), Alt+letter is still ignored. Every event sets `code`: without it `fireEvent` gives `""`, which is
not a digit.
